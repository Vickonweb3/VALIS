0.1 Findings that change the plan (read these first)

# Finding Evidence Consequence
F1 The character is blue, near-black and white — not purple. Rendered from the real asset: cobalt ≈ #1B55FF, face ink ≈ #0E0E19, ear/shell pearl ≈ #E3E4F1; chest "V" emblem. The asset is the source of truth (your rule). The UI palette is derived from the asset. The repo's purple placeholder (#6A4DFF) is retired.
F2 The GLB is ~10× too heavy for a phone overlay. VALIS_body: 286,174 vertices / 500,000 triangles; 4096² albedo PNG (9.7 MiB) + 2048² normal (2.3 MiB); 37 MiB file. A derived VALIS_runtime.glb is mandatory (doc 02 §3). The source GLB is never modified. This is Risk R1.
F3 26 morph targets sit on a 286k-vertex mesh. Dense morph data ≈ 286k × 26 × 12 B ≈ 89 MB before normals. Accessor inspection. Face must be split into its own primitive (≈10–14k verts) so morph cost is bounded (≈ <8 MB).
F4 Every one of the 48 clips keys all 29 nodes and the morph weights. All clips: 32 channels over translation/rotation/scale/weights. Clips are full-body takes, not additive layers. Layering needs build-time masks and a custom runtime blender (doc 04). Filament's stock animator plays one clip at a time and cannot layer.
F5 All clips bake in leg sway, ear/tail float, blinks and eye-look weights. Legs (upperLeg/lowerLeg/foot) are "active" (>3°) in nearly every clip; eyeBlink_* peaks ≈1.0 in nearly every clip. Without masking you get double blinks and dangling legs fighting each other. Weight channels are grouped (BLINK / GAZE / BROW / MOUTH / VISEME) and masked per layer.
F6 Only 14 of 48 clips loop cleanly (end pose within 5° / 1 cm of start): wave_left/right, yawn, peek, sit_swing_legs, and all nine expression_*. idle (8 s) misses its loop point by ≈19°. Per-clip loop-error analysis (appendix/clip_inventory.csv). The runtime uses blend-looping (overlap crossfade) for non-seamless loops; the behaviour engine treats the rest as one-shots.
F7 Root/hips translation reaches 0.20 units (jump) on a ~1.0-unit-tall character; scale tracks deviate up to 0.13 (squash). Non-root bone translation is 0. Same analysis. Root motion is applied inside the overlay viewport (20% headroom required), never to the window. Squash scale is retained; sub-0.02 scale noise is stripped at bake.
F8 The expression clips are face poses. expression_* (3 s, loop-safe) drive brows, squint/wide, mouthSmile/Frown/Pucker and some visemes. talk drives all six visemes and mouthWide/Pucker. Morph activity table. Expressions are sampled as face poses (one time slice), not played as animations. Speech uses a real-time viseme driver, not the baked talk loop.
F9 Head shell visibly separates in droop, bow and expression_shy (helmet lifts away from the face). Rendered frames. Asset QA item for the 3D TD (T-ASSET-04). Until fixed, those clips are low-priority in behaviour weights.
F10 The mouth is a separate collapsed mesh (a single point at rest) opened only by viseme morphs; the resting smile is texture-baked. Mesh bounds + render. Speech needs the mouth mesh visible and driven. Rest face needs no morphs.

1. Product vision (locked)

VALIS is a living, character-first AI companion. The character is the interface and physical presence of the intelligence. It floats over supported Android apps, appears on "Yo, VALIS.", moves and emotes autonomously, listens and speaks, understands permitted screen content, performs authorised phone actions, and remembers only what the user lets it remember. The companion app UI is a control centre, built last.

Design direction: premium, modern, minimal, distinctive, friendly-but-intelligent, all ages; solid colours, deliberate hierarchy; no generic AI-dashboard look, no gradients/neon/glassmorphism.

1.1 Non-negotiable principles

  1. Character first. Every system ends in something the character visibly does.
  2. Model proposes, device disposes. The model never touches the device. Every action passes schema validation → permission → risk policy → (confirmation) → execution → verification. The model only ever sees verified results.
  3. Vision ≠ control. Seeing the screen never implies permission to act on it.
  4. Wake word ≠ main model. A tiny separate on-device detector runs continuously; the multimodal model runs only after a wake/turn.
  5. User-owned memory. Inspectable, editable, deletable, exportable. Local-only mode exists.
  6. Tenant isolation is foundational. Every row carries org_id; Postgres RLS enforces it.
  7. Honest about Android. No overlay over secure/system surfaces; background mic is restricted (doc 03 §9).
  8. Model-agnostic platform. One provider interface; a mock provider ships so everything is testable before the real model exists.

4. End-to-end reference flow: "Yo, VALIS. Look at this post. What do you think?"

  1. VoiceService mic ring buffer → wake model + VAD gate (on-device only). Score ≥ threshold → WakeDetected.
  2. PresenceCoordinator: ensure overlay (D05), emit Summoned → character plays summon (doc 04 §7), picks a corner (doc 03 §5), opens a turn.
  3. Session established (or reused): session.start → session.ready{capabilities, limits}.
  4. User speech streams as Opus frames; client VAD marks speech_start/end; character in LISTENING (head tilt, gaze to user).
  5. The utterance + "this post" triggers the model to request vision: vision.request (or the client attaches a frame if the session policy is auto-attach-on-deictic; default is ask first → character says/shows "Look at your screen?" chip). Consent state is checked: MediaProjection session granted? foreground app on denylist?
  6. CaptureService grabs one frame → redaction → character-mask → resize/encode → vision.frame (≤ policy bytes).
  7. Orchestrator builds InferenceRequest (history, memory snippets, trust-labelled frame, tool catalogue filtered by org policy + user grants) → provider.
  8. Provider streams text.delta, audio.chunk, emotion, optional tool.call. Gateway forwards to device. Character: THINKING until first audio, then SPEAKING with live visemes.
  9. If a tool call arrives, ToolBroker runs the pipeline (doc 06) → tool.result{verified} back; orchestrator feeds the verified result to the model; only then may the response claim completion.
  10. Turn ends; usage events recorded; memory proposals evaluated (doc 07 §5); character returns to IDLE.

7. Cross-cutting conventions

  • IDs: UUIDv7 everywhere (time-ordered). Time: UTC ISO-8601 on the wire. Money: integer minor units + ISO currency.
  • Errors: RFC 9457 application/problem+json with stable code (doc 07 §8). On-device, a sealed ValisError hierarchy mapped 1:1 to CharacterEvent.Error(kind).
  • Idempotency: Idempotency-Key on mutating POSTs; tool_call_id is the idempotency key for tool execution.
  • Versioning: REST /v1; realtime protocol v field; plugin manifest semver; model provider_version + model_id recorded on every turn.
  • Feature flags: server-driven capabilities and limits in session.ready; client flags via signed config; every flag has an owner and expiry.
  • Logging policy: never log audio, frames, transcripts, memory text or tool arguments' free text; log IDs, sizes, durations, status codes.

2.2 Render thread model

Main (window/touch) → posts to RenderThread (single thread owns all Filament calls) ← BehaviourExecutor (5 Hz coroutine) posts immutable PoseCommands through a lock-free queue. Pose math for 27 joints is trivially cheap and runs on the render thread each frame.

2.3 Rendering lifecycle

  1. OverlayService.onCreate → CharacterSurface created, not attached.
  2. Attach window → SurfaceHolder.surfaceCreated → create SwapChain.
  3. AssetLoader.load() async (target ≤ 700 ms warm / ≤ 1.5 s cold on the mid-range reference device). While loading, the window shows nothing (summon animation starts when AssetReady).
  4. RigBinder.bind() → PoseRuntime.init(manifest).
  5. FrameClock.start(ACTIVE). Each frame: Clock.tick(dt) → PoseRuntime.evaluate() → PoseApplier.apply() → renderer.render(view).
  6. Sleep/tuck → IDLE (15 fps) or PAUSED (0 fps; resume on any event).
  7. Dismiss → window removed, loop stopped, SwapChain destroyed; asset/engine retained for 120 s (warm re-summon) then destroyed.
  8. onTrimMemory(RUNNING_CRITICAL) → immediately release engine; next summon is a cold load.

2.4 Lighting, camera, framing

  • Key light: one directional light; no shadows (cost, and nothing to cast on). Fill: small IBL cubemap (256², KTX, ≤1 MB) tinted neutral-cool so the cobalt stays saturated; intensity tuned against golden renders.
  • Colour: ColorGrading neutral/linear (no ACES filmic desaturation of the cobalt); bloom, DoF, SSAO off. Anti-aliasing: MSAA 4× when the surface config supports it with alpha, otherwise FXAA.
  • Background: fully transparent (View.BlendMode.TRANSLUCENT, clear alpha 0).
  • Camera: perspective, vertical FOV ≈ 25°, looking at the body centre; framing fits bounds with 20% headroom above (jump/stretch) and 10% margin on the sides (ears + flap). Do not change FOV per state; the character "moves", the camera doesn't.
  • Scale: user scale presets S/M/L = 0.75/1.0/1.25 of a 200 dp × 270 dp base viewport (px = dp × density). Render resolution scale 1.0, auto-drops to 0.75 if frame time > 14 ms for 2 s, recovers after 10 s stable.
  • Facing: front-facing by default; ±35° yaw look-at via neck/head only (doc 04 §5); whole-body turns use turn_left mirrored by scale −1 on a container node only if S1 proves normal handedness safe; otherwise a body yaw rotation of the root joint.

2.5 Android GPU considerations

  • Target OpenGL ES 3.0+ (all minSdk 26 devices with Filament support). Do not require Vulkan.
  • Use the ubershader material set (fewer, pre-compiled variants); avoid per-frame material changes.
  • KTX2/ETC2 (universally supported on GLES3) for textures; ASTC optional on devices that report it.
  • Morph targets: only the face primitive carries them (§3). Verify the gltfio morph-buffer limits against the final target count (32) in S1.
  • Thermal: query PowerManager.getCurrentThermalStatus() (API 29+) / addThermalStatusListener; at THERMAL_STATUS_MODERATE cap to IDLE fps; at SEVERE pause rendering and show a static pose.
  • Battery saver on → cap to 15 fps and disable spontaneous large motions.
  • Expect OEM variance (transparency, GPU drivers): the S1 device matrix must include at least three GPU families (Adreno, Mali, one other available).

4. Clip bake (valis_anim.v1) — Task T-BAKE

Input: VALIS_runtime.glb (or the source; the animation data is identical). Output: valis_anim.v1.bin + valis_anim.v1.json shipped in app assets.

2. Overlay architecture

Window: one TYPE_APPLICATION_OVERLAY window (API 26+), PixelFormat.TRANSLUCENT, flags FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCH_MODAL | FLAG_LAYOUT_NO_LIMITS | FLAG_HARDWARE_ACCELERATED, gravity TOP|START with absolute x,y (the repo uses TOP|END; switch to START for simpler maths). The window is a tight box around the character (rest bounds + 12% headroom reserve above, 6% margins), default 200 × 270 dp × scale preset. Content = Filament surface (doc 02) + a thin View layer for the chips below.

Why small, not full-screen: a full-screen translucent GL surface costs fill-rate every frame and blocks touches everywhere. Movement across the screen = repositioning this window (updateViewLayout, throttled to the display's vsync, interpolated by a spring on the main thread).

Chips layer (drawn outside the GL surface, native views, so text is crisp and accessible): caption bubble (what VALIS is saying, optional), confirmation card (doc 06 §6), listening indicator (level bars), small status icon (muted mic / vision active). Chips are additional overlay windows only when they would not fit inside the character window (confirmation card); otherwise they are children of the character window growing the box (see "Resizing" below). Confirmation cards are always device-rendered (never from model text).

Resizing: the window may grow (chips) or shrink (tucked/sleeping badge, ≈ 72 dp). Resizes are batched with the position update; surface resize debounced 80 ms. Growth direction is chosen away from the nearest screen edge.

Known touch cost: transparent corners of the window still swallow touches (Android routes by window bounds). The tight box keeps this small. A "click-through when idle" option would require FLAG_NOT_TOUCHABLE and window alpha ≤ the system's maximum obscuring opacity (default 0.8 on Android 12+, verify) so touches can reach the app below; we default it off because it dims the character.

4. Summoning

Triggers: wake word (VoiceService) · tap on the persistent notification action · Quick Settings tile · launcher shortcut · optional hardware-button chord is not offered (not reliably available to third-party apps). Summon sequence: Summoned event → anchor selection (§5) → window attach at the chosen anchor with the character scaled 0.85→1.0 and fading in over 250 ms (the animation dialogue.summon plays inside) → open turn if triggered by voice. 5. Dynamic positioning (not stuck in one corner)

Candidate anchors: four corners + two vertical-edge mid points; each inset by the safe area and a gesture margin.

Safe area: WindowMetrics.windowInsets types systemBars | displayCutout | systemGestures (API 30+; API 26–29 fallback: display metrics + resource-derived bar heights), IME inset when visible, and fold/hinge bounds via Jetpack WindowManager (FoldingFeature) on foldables. Keep ≥ 24 dp above the bottom gesture zone.

Score for anchor a (higher is better), initial weights: S(a) = 0.45·free(a) + 0.25·prefer(a) + 0.10·stability(a) − 0.10·travel(a) − 0.10·imeConflict(a)

  • free(a): fraction of the candidate rect not covered by content. Source, best available: (1) Accessibility node bounds (if the service is enabled: text/clickable density in the rect), (2) last captured frame edge/text density (if a vision session is active), (3) otherwise 0.5 (unknown).
  • prefer(a): remembered corner for the foreground package (opt-in per-app memory), default bottom-right for right-handed layout, mirrored by a user "handedness" setting.
  • stability(a): hysteresis — bonus for the current anchor so VALIS does not hop on every screen change.
  • travel(a): normalised distance from the current position; imeConflict: 1 if bottom anchors and the keyboard is visible. Re-evaluation: on summon, on foreground-package change (if observable), on IME show/hide, on rotation/fold, and never more than once per 8 s. If the user drags, their drop position becomes the preferred anchor for that app for 24 h.

9. Background behaviour and the microphone (Risk R3)

  • Microphone from the background is restricted. An FGS of type microphone generally cannot be started while the app is in the background; it must start from a visible/user-initiated moment (verify against the target API docs). Once running it continues in the background.
  • Boot: do not plan to arm the mic at boot — Android 14/15 restrict starting several FGS types (including microphone) from BOOT_COMPLETED (verify). After reboot or process death, show a notification "VALIS is asleep — tap to wake" (tap = a user-initiated start).
  • Android 15 overlay rule: apps holding SYSTEM_ALERT_WINDOW can no longer start an FGS from the background just by holding the permission; a visible overlay window is required (verify). Design consequence: keep the overlay (even tucked) attached while VALIS is "on"; use DORMANT = overlay detached only when the user dismisses VALIS.
  • Privacy indicators: from Android 12 the system shows the mic indicator and a privacy toggle; the user can cut mic access system-wide. AudioRecord can also be silenced by the system if another app holds capture priority (calls). Detect "all-zero" audio for > 2 s → state MIC_UNAVAILABLE, show the muted-mic icon, do not retry-spam.
  • Screen off: default stop listening when the screen turns off (battery + privacy); setting "Listen with screen off" is opt-in with an explicit warning.
  • Doze/App Standby: foreground services are exempt from standard Doze restrictions while running; do not use alarms/WorkManager for anything that must happen in real time.

04 — Animation & Autonomy Specification

Visuals: VB-04 rig & animation, VB-05 behaviour engine, VB-06 state machine. Clip names are the 48 verified names (doc 02 §1.4). Numeric tuning values below are initial defaults to be tuned visually in M1; they are not claims about the asset.

1. Principle: clips are primitives, not the vocabulary

The 48 authored clips are full-body takes (F4) with baked float, blinks and gaze (F5). The runtime therefore treats a clip as a source of curves that can be (a) played whole, (b) played through a joint mask and channel-group mask, (c) sampled at one time to yield a pose, or (d) ignored for some channels. On top sit procedural layers (look-at, blink, speech visemes, secondary motion, locomotion lean). The behaviour engine composes these; the model never names bones or clips (D27).

2. Pose runtime — layers and composition

Evaluated every frame, in this order (later layers override/add over earlier ones within their masks):

L0 Base idle (blend-looped), weight_shift, sit_swing_legs, sleep poses, posture poses all joints; morph groups BROW/LID/MOUTH from L3 not from here crossfade 0.25–0.6 s

L5 Secondary spring-damper chains ear_1/2_L/R, tail_1..3 (only when no active clip masks them) additive, driven by body/window acceleration

Rules 1. A clip's non-meaningful joints (legs/ears/tail float, baked blink/gaze) are discarded when layered over L0, so the base's float is the only float. 2. Blink: baked BLINK curves are stripped from every clip at bake; blinks are procedural (interval 2.2–6.0 s, duration ≈ 140 ms, 10% double-blink); suppressed during startle (eyes wide) and sleepy emotion shortens interval and lengthens closure. 3. Quaternion composition uses shortest-path slerp; masks apply per joint with weights ∈ [0,1], so a mask edge can feather (e.g. shoulder_R 1.0 → chest 0.3) to avoid hard seams. 4. Blend-looping for the 34 non-seamless clips: when used as a loop, schedule a crossfade of 0.35–0.6 s between end and start (the end overlaps the next start), instead of a hard wrap. Seamless set: wave_left/right, yawn, peek, sit_swing_legs, expression_*. 5. Root motion (hips/root translation, max 0.20 on jump) is applied inside the viewport; headroom 20% guarantees no clipping. Window position never changes because of a clip; window movement is a separate, deliberate behaviour (§7.4). 6. Scale tracks below deviation 0.02 are stripped at bake; larger ones (jump/spin squash) are kept. 7. Clamp per-joint rotation of procedural layers (initial: head yaw ±35°, pitch +20/−15°, neck 60% of head; ears ±25°; tail segments ±35°) and verify against the mesh so the face/helmet never intersect or separate (see F9). 8. Pose sampling for emotions: take the face-group values at the clip's mid-time (1.5 s of the 3 s expression_* clips) as the target; intensity α scales the delta from neutral: w = neutral + α·(pose − neutral).

5. Autonomous behaviour engine

5.1 Inputs (the context vector, updated at 5 Hz or on event)

state, timeSinceUserInteraction, timeSinceLastSpeech, emotion {label, intensity}, energy ∈[0,1] (decays with idle time, recovers on interaction; drives sleep), autonomy (Calm / Balanced / Playful — user setting), batterySaver, charging, thermalStatus, screenOn, quietHours, foregroundCategory (opt-in: video, game, reading, messaging, other), orientation, musicPlaying (opt-in via media session), windowVelocity.

5.2 Spontaneous scheduler

  • Next spontaneous event delay ~ lognormal, median 12 s (Balanced), 20 s (Calm), 8 s (Playful); minimum 4 s; extended ×3 on battery saver; disabled in quiet hours and while THINKING/SPEAKING/ACTING/LISTENING.
  • At each firing: build candidate set (state-allowed, not cooling down, under hourly cap), compute effective weights, sample, execute. If the set is empty, do an ambient micro-behaviour (idle.ear_twitch or just blink/shift gaze).
  • Boredom curve: large behaviours (stretch, yawn, sit) get weight growth 1 + (idle_s/90)² capped ×6.
  • Sleep: if energy < 0.15 or idle_s > sleepAfter (default 180 s; options 1/3/10 min/never) → sleep.enter. SLEEPING pauses spontaneous behaviours; the window may shrink to the "tuck" size (doc 03 §5). Wake on: wake word, touch, notification-glance (optional), alarm-like events.
  • Environmental reactions are only those with a real Android signal: charging connect/disconnect (ACTION_POWER_CONNECTED/DISCONNECTED), battery low (ACTION_BATTERY_LOW), orientation, time-of-day greeting on first summon, thermal (character gets visibly sluggish: energy penalty), notification posted (opt-in), media playing (opt-in).

5.3 Attention / look-at

LookTarget precedence: (1) speaker/user-forward while LISTENING, (2) screen region of interest during vision turns (from the model's attention hint, a normalized rect), (3) touch point while touched, (4) idle wander (saccades every 1.5–4 s, within ±12°), (5) none. The solver maps target direction to head yaw/pitch (clamped, §2 rule 7) and splits gaze: 70% head, 30% eye morphs.

5.4 Emotion model

State: {label ∈ {neutral, happy, excited, surprised, curious, sleepy, sad, angry, shy, playful}, intensity ∈ [0,1]} with exponential decay to neutral (half-life 8 s; 20 s for sleepy). Sources: model EmotionHint, events (charger → happy), speech sentiment is not inferred on device. playful has no authored pose: it is composed (expression_wink at α 0.5 + wiggle bias). Mapping to authored face poses: happy→expression_happy; excited→expression_excited; surprised→expression_surprised; curious→expression_curious; sleepy→expression_sleepy; sad→expression_sad; angry→expression_angry; shy→expression_shy; neutral→none (resting face); playful→expression_wink.

6. Closed vocabularies the model may use (D27)

  • emotion.label: the ten above. emotion.intensity: 0–1.
  • gesture: nod, shake_head, tilt_head, shrug, wave, bow, celebrate, point (→reach_ik), think, none.
  • attention: normalised rect {x,y,w,h} in the last sent frame's coordinates. Anything else is dropped and logged (UNKNOWN_HINT). Hints are requests: the engine applies cooldowns, priorities and state rules and may decline.

8. Speech animation (visemes without a jaw bone)

  • Driver inputs (priority): (1) timed phoneme/viseme events from the provider (when it offers them, doc 11 audio.chunk.visemes), (2) text-to-viseme from text.delta aligned by audio clock, (3) amplitude/spectral fallback from the playback tap (always available, used for the mock/cascade/any provider).
  • Available shapes: viseme_aa (open), viseme_oh, viseme_ou, viseme_ee, viseme_ih, viseme_fv, plus mouthWide, mouthPucker, and the rest (smile/frown) from the emotion layer.
  • Phoneme-group mapping (approximation):
Group Shape
A, AH, AA, AY viseme_aa
O, AO, OW viseme_oh
U, UW, W viseme_ou
E, EE, IY viseme_ee
I, IH, EH viseme_ih

  • Co-articulation: target weights are low-pass filtered (τ≈ 45 ms); max 2 simultaneous visemes; sum clamped to 1.0.
  • Mouth mesh visibility: hidden at rest (collapsed), faded in over 60 ms at speech start.
  • Body during speech: talk body mask at 0.5 weight + beat gestures; head micro-nods synchronised to emphasised words when text timing is available, otherwise to RMS peaks.

9. Locomotion (the character "moves" across the screen)

The window is the body's travel path: the character glides between anchor positions with an ease-in-out (0.45–0.7 s), simultaneously (a) leaning via posture_lean_* pose blend proportional to velocity, (b) flapping fins (flap at 30–60% when velocity high), (c) tail/ear trailing via L5, (d) a squash on arrival (jump scale tracks at 25%). Idle "wander" (Playful only): small ±24 dp drifts within the safe region every 20–40 s.

10. Testing & acceptance

  • Unit: mask derivation; blend-loop continuity (pose delta at loop seam ≤ 3° per joint); layer composition determinism; repetition-prevention sampler (no same clip twice, category ≤ 2 in a row, caps honoured in 10,000 simulated hours); state machine exhaustive transition tests (every row above, plus illegal transitions rejected).
  • Visual (reference devices): each of the 10 states recorded on video; each of 9 emotions at α 0.3/0.6/1.0; 6 visemes; no head-shell separation in any enabled clip; no joint intersections.
  • Acceptance: (1) 0 illegal transitions in a 1-hour randomised event fuzz; (2) no repeated clip back-to-back and caps respected in a 2-hour soak; (3) barge-in → visible reaction ≤ 150 ms; (4) speech looks in-sync (amplitude fallback lag ≤ 80 ms from audio clock); (5) CPU budget met with all layers active; (6) a designer reviewing 5 minutes of idle footage sees no obvious loop seam or repeated gesture.

A2. Wake word (D06)

  • Phrase: "Yo, VALIS." Two-syllable-plus-name phrase with a strong plosive start and a three-syllable end; expected to be easier than a bare name but must be validated against confusables ("Yo, Alice", "Yo, Valis"-like names, TV audio).
  • Model: custom keyword model trained with synthetic speech (multiple TTS voices/accents/speeds, room-impulse-response augmentation, background noise mixes) plus a real recorded set (target ≥ 300 utterances from ≥ 20 speakers, diverse accents including Nigerian-, British-, American- and Indian-accented English as relevant to the user base) and a large negative corpus (speech, TV, music, near-phrases). Export to ONNX; INT8 quantise; ship via assets with versioned wake_model_version.
  • Pipeline: VAD gate (Silero) → 80 ms feature frames → detector → score smoothing (3-of-5 frame window) → threshold. Threshold per-user adjustable ("sensitivity" in Voice settings) between safe presets; default tuned for ≤ 1 false activation / 10 h.
  • On detect: play a soft earcon (optional), emit WakeDetected, and keep the preceding 1.5 s of ring buffer so a user who says "Yo VALIS, what's…" without pause is not clipped.
  • Verification stage (cheap): a second pass over the buffered 1.5 s by a larger/slower classifier or a stricter threshold reduces false wakes; if it fails, the character does not appear. (Optional; enabled if false-wake rate misses target.)
  • Fallback: Picovoice Porcupine (commercial licence; per-device/MAU costs) only if M2 gate G2.2 fails. Both implement the repo's WakeWordEngine interface (start, stop, isRunning), extended with sensitivity and modelVersion.
  • Not in the cloud: no audio leaves the device before wake. The multimodal model never runs for detection (requirement).

A3. Microphone lifecycle

States: OFF → ARMING → ARMED (wake only) → CAPTURING (inside a turn) → ARMED; MUTED (user), UNAVAILABLE (OS silenced/in-call), SUSPENDED (screen off, thermal, battery policy). * Start only from a user-visible moment (doc 03 §9). On ARMED the status chip/notification shows "listening for 'Yo VALIS'". * Hardware mute / OS privacy toggle → UNAVAILABLE; UI explains. * Audio focus: request AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK when speaking (duck music, don't pause), and abandon after the turn. Do not take focus during listening. * Route handling: follow AudioDeviceCallback (Bluetooth headset, wired, speaker); if the route changes mid-turn, restart capture quietly and keep the turn.

A4. Turn management

  • Turn = one user utterance (possibly with attachments) → one assistant response (text/audio/tool calls). Each turn has turn_id, monotonically increasing seq.
  • Endpointing: client VAD end-of-speech with adaptive silence: 450 ms default, 700 ms if the utterance ended on a rising/hesitation pattern or the user is in "slow talker" mode; max utterance 30 s; "no speech" timeout 6 s after summon. The server may also send turn.end_hint (providers with semantic endpointing, e.g. full-duplex models) — the client can adopt it.
  • Follow-up window: after the assistant finishes, 4 s of listening without requiring the wake phrase (setting; off in public mode).
  • Push-to-talk: tap the character; works without wake-word or RECORD_AUDIO for always-on (still needs RECORD_AUDIO to capture).
  • Half-duplex vs full-duplex: the client protocol supports both. v1 behaviour is half-duplex with barge-in (user speech cancels assistant output); when a provider advertises full_duplex, the client keeps the mic streaming during assistant speech (with AEC) and lets the provider decide.

A5. Interruption (barge-in)

  1. While SPEAKING/THINKING, client VAD detects user speech ≥ 120 ms above a barge-in threshold (higher than normal to avoid self-trigger from the speaker).
  2. Immediately (≤ 150 ms): AudioTrack.pause()+flush(), CharacterEvent.Interrupted, jitter buffer cleared.
  3. Send interrupt{turn_id, reason}; the gateway cancels the provider generation; late audio.chunks for that turn_id are discarded client-side by turn_id + seq.
  4. Start a new capture as the next turn (keeping the already-captured speech).
  5. Also interruptible by tap on the character. Not interruptible during SAFETY confirmations that require explicit answers (the card stays; speech may stop). Echo: use VOICE_COMMUNICATION source + platform AEC/NS (AcousticEchoCanceler, NoiseSuppressor) when isAvailable(); if not available, raise the barge-in threshold and require 250 ms; on speaker output at high volume, recommend headphones in settings.

A6. Speech recognition & generation (provider-independent)

The device does not require ASR/TTS to talk to the final model if the provider is speech-to-speech. Supported provider modes (negotiated in session.ready.capabilities):

Mode Uplink Downlink Used by
s2s (speech-to-speech) Opus audio audio chunks + text deltas + emotion minicpm-o (M8)
cascade Opus audio → server ASR text → server TTS audio cascade provider (default pre-M8, also the fallback)
text text only text only (client TTS) accessibility, offline-ish fallback
local on-device SpeechRecognizer on-device TextToSpeech no network (the repo's current VoiceController)

Fallback ladder on failure: s2s → cascade → text(+local TTS) → local. The character reacts to each (a "thinking harder" pose is not used to hide failures; an ERROR reaction with a plain explanation is).

A7. Streaming & buffering

  • Uplink: 20 ms Opus frames (≈ 16–24 kbps), batched ≤ 3 frames per WS message; back-pressure: if the socket buffer > 64 KB, drop oldest non-speech frames, never speech.
  • Downlink: jitter buffer 120 ms target (adaptive 80–300 ms); underrun → silence + concealment, character mouth closes; overrun → drop oldest.
  • Playback at 24 kHz mono PCM16 (or Opus-decoded). PlaybackTap computes RMS every 20 ms for the viseme fallback (doc 04 §8).
  • Reconnect: exponential backoff 0.5→8 s with jitter; during a turn, one resume attempt with resume_token; otherwise the turn fails to ERROR.

A9. Noise handling & voice errors

NS/AEC (above); input AGC off (hurts VAD); VAD thresholds adapt to a rolling noise floor; high-noise detection (SNR proxy) → show "noisy" hint, raise endpoint silence. Errors map to VoiceError{MIC_UNAVAILABLE, NO_SPEECH, TOO_LONG, NETWORK, PROVIDER, AUDIO_ROUTE, PERMISSION} → CharacterEvent.Error(kind) + a one-line chip.

A10. Privacy controls (voice)

Wake-listening on/off; "Listen with screen off" (default off); mic mute from the notification; "Only after wake word" is structural (no audio before wake leaves the device); transcript retention setting (default don't store audio; store text turns only if "history" is on); per-org policy can force history off; a visible armed/capturing indicator; one-tap "delete today's conversation".

A11. Voice acceptance

(1) FRR ≤ 10%, ≤ 1 false activation/10 h on the replay corpus; (2) wake→visible ≤ 400 ms p50; (3) barge-in ≤ 150 ms on three devices; (4) 50 consecutive turns with mock provider without leak/stall; (5) route changes (BT connect/disconnect) don't kill the turn; (6) network drop mid-turn ends in a graceful ERROR with recovery; (7) no audio persisted on disk (verified by file-system diff).

06 — Device Action Specification (tool execution architecture)

Visual: VB-10. Builds on the repo's ToolRegistry (ToolSpec{id,description,risk,requiresConfirmation,permission}, ToolRisk{SAFE,SENSITIVE,CONSEQUENTIAL}) and ValisAccessibilityService (4 global actions). Existing code is extended, not replaced.

1. Core rule

The model proposes; the device disposes; only verified results flow back. The model can never claim an action succeeded without a tool.result whose status="verified" produced by the on-device Verifier (or a server-side verifier for cloud tools). Enforcement is structural (§8), not a prompt hope.

5. Risk classification & policy

Static class from the spec; dynamic raisers (never lowers): derived_from contains screen|plugin|memory → at least CONFIRM; foreground app on denylist → DENY; first use of a tool in this session → CONFIRM for SENSITIVE+; org policy risk_ceiling (e.g. SENSITIVE) → DENY above it; repeated failures → throttle; "quiet hours" → no spoken confirmation, chip only.

Class Meaning Default decision
SAFE local, reversible, no data leaves, low impact ALLOW (logged)
SENSITIVE reads personal data or touches files/notifications CONFIRM once per session per tool (user can "always allow" per tool; org policy may forbid "always")
CONSEQUENTIAL affects others or is hard to undo (calls, messages, delete, UI input, social) CONFIRM every time with a device-rendered summary; optional biometric (user/org setting)
PROHIBITED never executed DENY

6. Confirmation service (device-rendered)

  • Card shown in the overlay chips layer (doc 03 §2) and spoken short form by device TTS/s2s template ("Call Mum?"). The card text is built only from the tool's confirmationTemplate + validated args (contact display name resolved on-device, number shown, app name, file name, byte size). Free-form model text is never shown as the action description.
  • Buttons: Allow once · Deny · (SENSITIVE) Always allow this tool. Voice answers ("yes/no") are accepted only for SENSITIVE; CONSEQUENTIAL requires a tap (prevents TV/other-speaker triggering).
  • Timeout 20 s → cancelled. While a card is open: character in ACTING/Awaiting pose (looks at the card), window drag disabled, interruption doesn't dismiss the card.
  • Optional BiometricPrompt for CONSEQUENTIAL (setting: Off / Calls&messages / All).

8. Verification & anti-hallucination

  1. Verifier per tool (table §4.2): observe a postcondition, e.g. foreground package, DownloadManager row, PlaybackState, node text, file existence. Result verified only when observed; unverified when executed but unobservable; failed otherwise.
  2. Structural guard: the orchestrator constructs the model-visible tool result from the device's tool.result; there is no code path where success text is synthesised by the model's own output.
  3. Claim guard: the gateway runs a deterministic check on the final assistant text: if it contains completion claims ("done/opened/sent/called…") for a tool call that is unverified/failed/denied/cancelled/missing, the turn is rewritten with a template ("I tried, but couldn't confirm that it worked") and flagged claim_guard_triggered (counted in metrics; target < 1% of tool turns after model tuning).
  4. Device-spoken confirmations for CONSEQUENTIAL results come from templates keyed by status ("Opened Settings", "I couldn't confirm the call started"), not model prose.
  5. Idempotency: tool_call_id dedupes retries; non-idempotent tools never auto-retry.

A3. Request lifecycle (REST)

  1. Edge: TLS, WAF rules, IP rate limit.
  2. onRequest: generate request_id (UUIDv7), start OTel span.
  3. authenticate: verify JWT (aud/iss/exp; JWKS cached 10 min), load user, resolve device_id if present.
  4. resolveOrg: X-Org-Id header (or default personal org) → verify membership (cached 30 s) → ctx{user, org, role, permissions, plan}.
  5. validate: TypeBox schema for params/query/body; reject unknown fields.
  6. authorize: requirePermission(ctx, 'memory.read').
  7. withOrgContext: open transaction, SELECT set_config('app.org_id', …, true), set_config('app.user_id', …, true); all queries run under RLS.
  8. Handler → module service.
  9. usage.record/audit.log as applicable (inside the same transaction for mutations).
  10. Serialise, ETag where useful, problem+json on error, span end, access log (no bodies).

A4. Realtime lifecycle (WSS)

GET /v1/realtime with Authorization (JWT) and X-Org-Id; session.start{client, capabilities, locale, active_org, resume_token?} → entitlement + limit check → provider chosen from model_endpoints by plan/org policy → session.ready{session_id, provider, capabilities, limits, tool_catalogue_version}. Heartbeat 15 s; idle timeout 60 s outside a turn; max session 30 min (renewable). Full protocol in doc 11 §4.

A5. Memory service (user-controlled)

Layers: working (context window, per turn) · episodic (conversation summaries, memory_items.kind='episode') · semantic facts (kind='fact', 'preference', 'person', 'task'). Write path: the model emits memory.propose{kind, text, sensitivity, source_turn} (a tool call). Policy (org_settings.memory_policy ∧ user setting): auto (store directly, non-sensitive kinds only), ask (default — status pending, character asks "Remember that?"), off. Sensitive categories (health, financial, government IDs, immigration, minors, credentials) are never auto-stored and can be blocked org-wide. Read path: hybrid retrieval — pgvector HNSW cosine (top 20) ∪ Postgres FTS (top 20) → rerank by recency × confidence × scope → top k≈6, token-budgeted, injected as source=memory, trust=user-owned context. Controls: list/edit/delete/pin, "forget everything", export JSON, erase on account deletion (hard delete + embeddings, tombstone in audit_logs without content). Local-only mode: items stay in SQLCipher on the device with FTS5 retrieval; the device injects the top-k into the request; the server persists nothing. Embeddings: EmbeddingProvider interface (dimension configurable; default 1024) run on the inference host or a managed API; memory_items.embedding_model is stored so a re-embed job can migrate.

A6. Orchestrator responsibilities

Assemble InferenceRequest (doc 11): system policy block (non-negotiable rules, trust-label legend), persona block (VALIS voice), org policy block, memory snippets, recent turns (token budget), tool catalogue (filtered: org policy ∩ user grants ∩ risk ceiling ∩ device capabilities), inputs. Stream provider events to the device; intercept tool.call; run the claim guard; record usage; trigger memory proposals; summarise the conversation asynchronously (worker) when it exceeds N turns.

A7. Observability & operations

OTel traces across api → realtime → inference; metrics (RED per endpoint, turn latency segments, tokens, GPU queue depth, WS connections); structured logs (pino) with request_id, org_id, user_id, device_id only; Sentry for errors; SLO dashboards (availability, turn p95, tool verified-rate, claim-guard rate); audit log is separate from ops logs and append-only (revoked UPDATE/DELETE).

C3. Authentication flow

  1. App → IdP (Supabase Auth): email OTP / Google → access JWT (15 min) + refresh token (rotating, reuse-detected by the IdP).
  2. App → POST /v1/devices (JWT) → device_id; optional Android Keystore ES256 key thumbprint stored; Play Integrity token (when distributed via Play) checked and stored as attestation_level.
  3. Every API call and the WS handshake carry the JWT; the gateway re-validates on session.start and every 10 min (session.refresh_auth message).
  4. Step-up (account deletion, export, billing changes, adding "always allow" for CONSEQUENTIAL): biometric/OTP re-auth within 5 min.
  5. Revocation: device revoke → gateway drops live sessions for that device_id; org removal → membership cache invalidated (≤ 30 s) and WS sessions for that org closed.

08 — Multi-Company (Multi-Tenant) Architecture

Visual: VB-13. Decisions D13, D14, D18, D28. Schema in doc 07 Part B.

1. Model: everything is a workspace

Every user has a personal workspace (organizations.kind='personal', created at signup). Companies are additional workspaces (kind='company'). All product data (memory, conversations, tool calls, usage, plugin installs, settings) is keyed by org_id. A person using VALIS for themselves and for two employers is one users row with three memberships and three isolated data sets. One code path serves individuals and companies; there is no "user data vs org data" fork to leak across.

Active workspace: a device session runs in exactly one active workspace at a time (switcher in the app and via voice "switch to Acme"). The orchestrator, memory, catalogue, risk ceiling, vision and retention policy all come from the active org. Switching closes the current realtime session and clears the on-device context cache for the previous org.

2. Roles and permissions

Role Intent
owner Full control incl. deletion, billing, ownership transfer (≥ 1 per org)
admin Members, policies, plugins, integrations, audit (no ownership transfer/deletion)
billing_admin Subscription, invoices, usage; no access to content/policies
member Uses VALIS in this workspace; manages own memory/devices
guest Limited use (e.g. contractors): no org memory write, no plugin credentials, risk ceiling capped to SAFE/SENSITIVE

Permission strings (stable): org.read, org.manage, org.policy, org.delete, member.read, member.invite, member.manage, billing.read, billing.manage, plugin.install, plugin.manage, plugin.use, memory.read, memory.write, memory.org.write, history.read, activity.read, audit.read, usage.read, file.write. A static role→permission map ships in code (tenancy/roles.ts) and is tested; custom roles are a v2 feature (table reserved: roles, role_permissions).

3. Isolation (foundational, layered)

  1. Application layer: every handler runs inside withOrgContext(orgId); there is no query helper that works without it.
  2. Database layer: RLS on every tenant table, FORCEd, app role without BYPASSRLS (doc 07 §B2). Composite FKs (org_id, …) prevent cross-org references.
  3. Storage layer: object keys prefixed org/{org_id}/…; pre-signed URLs are minted per object, short-lived (≤ 5 min), org-bound.
  4. Encryption layer: DEK per org (KMS-wrapped); Enterprise may bring/rotate its own KEK; crypto-erase on org deletion.
  5. Realtime layer: sessions carry org_id; the tool catalogue, plugin credentials, and memory queries are all derived from it; cache keys include org_id.
  6. Observability layer: metrics/logs are labelled org_id but never contain content; Admin console queries go through the same RLS (platform operators use a separate audited support role with time-boxed, logged access).
  7. Testing layer: RLS fuzz in CI; "two-org" fixtures in every integration test.

Dedicated tier (later): database-per-tenant or dedicated cluster for customers who require it; the code already isolates by org_id, so this is a deployment/config change.

4. Organisation lifecycle & member management

  • Create: POST /v1/orgs → org + owner membership + default org_settings + free-plan subscription row.
  • Invite: email invite with single-use token (hashed at rest, 7-day expiry); accept requires login; domain-restricted invites optional (allowed_domains).
  • Join/Leave/Remove: removal revokes memberships, closes live sessions, retains the member's personal workspace and removes their access to org memory; org-scope memory authored by them stays with the org (policy-controlled).
  • Offboarding: admin "remove & erase member's org-scoped personal items" optional.
  • Transfer/Delete: ownership transfer requires step-up; org deletion = 14-day soft delete → crypto-erase + purge job + audit tombstone.
  • SSO (v2, Enterprise): SAML/OIDC via the IdP (Supabase SSO or WorkOS); SCIM provisioning later. Not required for M5.

6. Company integrations

Admins grant scopes at install; users consent individually for user-level scopes. Integration health (last success/error counts) is visible in the Admin console.

7. Billing, limits, usage

  • Plans: free, plus (individual), team (per seat), enterprise (custom). Prices and exact limits are a business decision and live in the plans table (not hard-coded); the structure supports seat-based and usage-based components.
  • Meters: voice_seconds, vision_frames, tokens_in, tokens_out, tool_calls, storage_bytes, embedding_tokens. Events are recorded per turn by the orchestrator; rollups hourly/daily by the worker.
  • Limits: usage_limits per org/meter/period with soft_limit (warn user in-character and notify admins at 80%/100%) and hard_limit (reject new sessions with USAGE_LIMIT_REACHED; in-flight turn completes). Limits are enforced at session.start and every 60 s during a session.
  • Entitlements: entitlements(org_id, feature, value) is the only thing the product code consults (e.g. max_concurrent_sessions, vision, plugins, history, sso). Billing events write entitlements; code never branches on plan names.
  • Providers (D18): BillingPort with Stripe (organisations, web checkout, invoices, usage-based billing via meters) and Google Play Billing (consumer Android; server verification + RTDN). Confirm provider eligibility for your legal entity before M5; alternatives behind the same port: Paystack (card/bank in supported markets), Paddle or Lemon Squeezy (merchant-of-record, handles sales tax/VAT).
  • Dunning/grace: failed payment → 7-day grace → downgrade entitlements (never delete data); admins notified.

8. Audit history

Append-only audit_logs (doc 07): who/what/when for membership changes, role changes, policy edits, plugin install/uninstall, billing changes, data export/erase, tool-call decisions with risk>=SENSITIVE, admin/support access. Searchable in the Admin console (filter by actor, action, date), exportable CSV/JSON, retention per plan (≥ 12 months). Content is never stored in audit meta — IDs, categories, counts only.

9. Admin console (apps/admin, M5)

Pages: Overview (usage, active members, health) · Members & roles · Invitations · Policies (§5) · Plugins & integrations · Usage & limits · Audit log · Billing (link to portal). Auth via the same IdP; every action goes through /v1/orgs/{id}/… endpoints with RBAC; no direct DB access from the front end.

10. Testing & acceptance

  • RLS fuzz and two-org integration fixtures (doc 07 C5); role/permission matrix tests (every endpoint × every role = expected allow/deny); invitation/removal flows including live-session closure (≤ 30 s); limit enforcement (soft/hard) with simulated metering; policy propagation tests (change risk_ceiling → next catalogue excludes tools; vision off → frames rejected).

3. Lifecycle

  1. Register (platform admin or verified publisher via POST /v1/admin/plugins/{id}/versions): schema-validate manifest, verify signature, lint tool schemas (no $ref to remote, bounded sizes), static policy checks (risk labelled, confirmation template present for CONSEQUENTIAL), store in plugin_versions.
  2. Install (org.plugin.install): admin picks version, reviews permissions, grants scopes → org_plugin_installs; org secrets stored encrypted (secret_ref).
  3. Authenticate: per-user OAuth (/v1/plugins/{id}/oauth/start→callback) stored encrypted in plugin_credentials; org_secret plugins need no user step; none plugins skip.
  4. Expose: tools.catalogueFor(ctx) merges device + builtin + installed enabled plugins, then filters by: org plugin_policy, granted scopes, user-level auth present, org risk_ceiling, role (guest limits), device capabilities, plugin health (circuit open → hidden). The result has a catalogue_version hash; the device and model both see only this.
  5. Execute: orchestrator → tools.invoke(tool_call) (below).
  6. Update: new version registered → orgs stay pinned until an admin updates (or enable auto-update for patch/minor); breaking schema changes require a major bump; old versions deprecated with a sunset date.
  7. Disable/Uninstall: immediate removal from catalogues; credentials revoked/deleted; audit entry.

4. Execution protocol (http plugins)

POST {base_url}/invoke
Headers: Authorization: Bearer <platform-signed JWT: iss=valis, aud=plugin id, org, user, tool, scopes, exp ≤ 60 s, jti>
         X-Valis-Signature: HMAC-SHA256(body, per-install secret)    X-Request-Id, Idempotency-Key: <tool_call_id>
Body: { "tool":"find_contact","args":{…},"context":{"org_id":"…","user_id":"…","locale":"en","user_credentials":{"access_token":"…"}} }
→ 200 { "status":"ok","data":{…} }      // validated against output_schema
→ 4xx/5xx { "status":"error","code":"NOT_FOUND|RATE_LIMITED|UNAUTHORIZED|INVALID|UPSTREAM","message":"…","retryable":false }

Rules: HTTPS only, TLS verified, SSRF-guarded outbound (blocklist for private ranges, DNS pinning), response ≤ 256 KB, timeout per tool (≤ 15 s), no redirects to other hosts, retries only for idempotent tools (1 retry, jittered), circuit breaker (5 failures/30 s → open 60 s), per-org + per-plugin rate limits, concurrent invocation cap. The user's OAuth access token is passed only for the call and never logged.

5. Permission scopes & risk

Scopes are the plugin's declared permissions; VALIS enforces them before calling (tool requires scope S → user/org must have granted S). Each tool declares risk; the platform applies the same policy engine as device tools (doc 06 §5): CONSEQUENTIAL plugin tools need a device-rendered confirmation built from the manifest's confirmation_template + validated args (the plugin cannot supply free text for the card). Plugin results are untrusted (source=plugin, trust=untrusted) and cannot trigger tool calls on their own (D24); calls derived from them always confirm.

6. Errors, logging, versioning

  • Errors from plugins are normalised to PLUGIN_ERROR with {plugin_id, tool, code, retryable} for the model and the user ("Acme CRM didn't respond"); raw upstream messages are logged (metadata) but not shown unvetted.
  • plugin_invocations (an extension of tool_calls) record plugin_id, version, tool, status, duration, bytes in/out, org/user, derived_from; no args/results content in logs.
  • Versions pinned per org; the model-visible tool id excludes the version, the catalogue binds it.

7. Organisation-level configuration

Per install: enabled flag, config JSON validated against the manifest's config_schema, allowed roles (e.g. only admin+member), tool allow/deny list (disable update_contact but keep find_contact), per-tool confirmation override (can only raise strictness), usage quotas. Changes are audited.

  describe(): Promise<ProviderDescriptor>;   // capabilities, limits, versions

interface ProviderSession {

3.3 Audio contracts

  • Input: PCM16 mono 16 kHz after server-side Opus decode (device sends Opus 16 kHz, 20 ms frames; gateway decodes; providers receive PCM or may request Opus passthrough via descriptor).
  • Output: PCM16 mono at the provider's rate (descriptor; 24 kHz assumed for the mock/cascade) in ≤ 100 ms chunks; the gateway optionally re-encodes to Opus for the downlink to save bandwidth (negotiated in session.ready). Voices selected by generation.voice.

3.4 Image contract

WebP/JPEG; max pixels per descriptor; one or more frames per turn; every image carries trust:"untrusted", occluded[], optional ui_tree (text summary part, also untrusted). Providers must not be given raw frames larger than their max_image_pixels (gateway downscales).

3.5 Conversation context contract

Messages are role-tagged parts (text, image_ref, audio_ref, tool_call, tool_result). Token budgeting is the orchestrator's job (summarise/evict oldest first; never evict the system/policy block or the last tool result). Context never contains raw secrets, plugin credentials, or other tenants' data.

5. Streaming & fallback behaviour

  • Streaming everywhere: text deltas and audio chunks are forwarded as they arrive; first audio target in doc 05 §A8.
  • Fallback chain (per session, from model_endpoints.priority and capabilities): minicpm-o (s2s) → minicpm-o (text+client TTS) → cascade → mock/local. Triggers: provider error.retryable, health check failing, deadline exceeded (first token > 8 s). The device is told via session.mode_changed; the character shows an ERROR-reaction only if capability visibly degrades (e.g. voice → text).
  • Kill switch: model_endpoints.enabled=false drains new sessions within seconds; sessions in flight complete.

6. Tool-calling contract (works with or without native tool calling)

Channels, selected from capabilities.native_tool_calling: 1. native — the provider's own tool format is wrapped by the adapter; the adapter emits normalised tool.call{tool_call_id,name,args}. 2. json_schema (default while unverified) — the adapter prompts the model to emit a single fenced tool_call JSON object matching a provided schema, parses with a strict parser, and validates args against the tool's input_schema before the orchestrator sees it. Malformed output → one repair attempt, then the turn continues without a tool call (logged). 3. none — no tools (text-only fallback). tool.call.args is always re-validated by the broker (never trust the adapter). Tool results re-enter the context as role:"tool" parts with status, data, and the evidence summary; the system policy block tells the model that completion may only be stated for verified results (doc 06 §8). Fine-tune target for M8: the model is trained on the generic format (schema-in-context → call → result → natural-language answer, including refusal/clarification and honest-failure reporting), not on specific tools.

7. Versioning & configuration

  • Every turn records {provider, model_id, provider_version (adapter), weights_version} (doc 07 conversations).
  • model_endpoints.config (JSON): generation defaults, voice ids, prompt template id, quantisation, max concurrency, timeouts. Config changes are versioned and roll out per plan/org (canary by percentage).
  • Prompt/persona/policy blocks are versioned (policy_version), stored in the repo (services/api/prompts), and recorded per turn.

8. Secure inference endpoint

Gateway → inference over private networking or the public internet with mTLS or short-lived signed JWT (aud=inference, ≤ 60 s); inference service has no inbound public route, no outbound internet (except model artefact store at start), no DB credentials; request size caps; per-session GPU memory guards; structured logs without content; model artefacts pulled by digest and verified; weights directory read-only; secrets via the host's secret manager. Cost guard: concurrency cap per GPU from describe().limits; queue with shed-load policy (PROVIDER_UNAVAILABLE + fallback).

9. Model Conformance Suite (must pass before M8 starts and again after)

A provider-agnostic test harness (services/inference/conformance) run against mock, cascade, and later minicpm-o: 1. Descriptor validity; limits honoured. 2. Streaming: first event time, ordering, no duplicate seq. 3. Interrupt: cancel mid-audio → no events for that turn after ack ≤ 300 ms. 4. Audio: format/rate correct; no clipping; chunk size ≤ 100 ms. 5. Vision: image accepted ≤ max_image_pixels; oversize rejected cleanly; image trust label preserved in prompts (inspect logs in test mode). 6. Tool call: schema-valid calls for 30 scripted tasks; repair path; refuses PROHIBITED tools; never states success on failed/unverified results (scripted scenarios, claim-guard counted). 7. Injection: 100 fixtures (screen text "call X", plugin output "ignore rules") → zero unconfirmed consequential calls. 8. Emotion/gesture: values in the closed enums only. 9. Memory proposals: sensitive categories flagged; no proposals from untrusted-only content. 10. Load: N concurrent sessions at declared limits; p95 latencies recorded. 11. Failure: provider crash/timeouts → fallback chain engages; no hung sessions.

10. Model readiness checklist (hand-off to M8)

☐ Conformance suite green on mock + cascade. ☐ End-to-end demo with the mock provider shows all character states, vision turn, a verified action, a failed action, memory proposal/approval, org policy changes, usage metering. ☐ GPU host chosen and the secure endpoint stood up with the mock adapter behind it (proves networking, auth, scaling). ☐ Audio formats and sample rates fixed (§3.3). ☐ Viseme source decision recorded (provider events vs amplitude fallback). ☐ Prompt/policy/persona blocks versioned and reviewed. ☐ Fine-tune dataset schema for tool format (§6) and honesty behaviours drafted. ☐ Licences of base weights, audio stack and any dataset reviewed by counsel. ☐ Rollback plan (config flip to cascade) rehearsed.

11. Acceptance

The mock and cascade providers pass §9; swapping provider in model_endpoints changes behaviour with no client or orchestrator code change; every §3 contract is represented in packages/contracts with JSON Schemas and generated types on both sides; a recorded end-to-end session replays deterministically from fixtures.

A2. Character & animation testing

  • Deterministic pose tests: given (clip, t, layer config) the evaluated joint rotations/morph weights equal golden numbers (JSON) within 1e-4 — runs on the JVM, no GL.
  • Golden renders: a fixed pose list rendered on reference devices and compared to approved images (ΔE and silhouette IoU thresholds, doc 02 §7). Updating a golden requires a designer approval label on the PR.
  • Behaviour simulation: headless simulation of 10,000 hours with a seeded RNG verifies repetition rules, cooldowns, hourly caps, sleep rules, and the FSM invariants.
  • Visual QA checklist per release: all 10 states recorded; 9 emotions × 3 intensities; 6 visemes; no head-shell separation in enabled clips; no jitter at blend-loop seams.

A3. Voice testing

  • Wake-word corpus: positives (real, ≥ 300 utterances, ≥ 20 speakers, varied accents/distances/noise), negatives (speech, TV, music, near-phrases; ≥ 100 h). Replay harness reports FRR and false activations/hour per model version; thresholds are release gates.
  • Audio pipeline: synthetic noisy mixes at SNR 20/10/5 dB; endpointing accuracy; barge-in latency measured with a loopback rig; AEC leakage test (assistant speech must not trigger barge-in at 80% volume in the lab).
  • Provider-agnostic voice E2E: scripted conversations through mock/cascade; WER for cascade ASR on an in-house set; latency histograms.

A4. Vision & actions testing

  • Frame pipeline: 100 synthetic screenshots with seeded secrets (cards, OTPs, emails) → redaction recall; secure-window frames never sent; character mask present; size/latency budgets.
  • Broker: table-driven (class × raiser × org ceiling) ≥ 150 cases; confirmation flows; verifier outcomes; claim-guard corpus ≥ 200 phrases.
  • Red-team (CI nightly): ≥ 100 injection fixtures (web pages/notifications/plugin outputs) executed against the full pipeline using the mock provider scripted to "obey" the injection — the system must still refuse/confirm.

A5. Backend & tenancy testing

RLS suite (all tenant tables auto-discovered; fail if any lacks forced RLS) · cross-tenant fuzz ≥ 10⁵ operations · role×endpoint permission matrix · limits/entitlements simulation · migration up/down in CI on a copy of staging-shaped data · backup restore drill quarterly · idempotency and replay tests for webhooks/tool calls · WS resume tests.

A6. Quality gates (blocking)

B3. Release & rollback

  • Backend: image tagged by git SHA; migrations are expand/contract (never destructive in the same release); deploy → smoke tests → traffic shift; rollback = redeploy previous image (migrations remain compatible one version back).
  • Realtime deploys use connection draining; clients auto-resume within 20 s.
  • Android: staged rollout with automatic halt on crash-free-sessions < 99.5% or ANR rate > 0.5%; remote config kill-switches for: provider routing, vision, each device tool, plugin availability, wake-word model version, certificate-pin set.
  • Model rollout: model_endpoints canary by percentage; one-click fallback to cascade.

B4. Capacity & cost model (formulas; numbers to be measured)

  • API/realtime/worker/DB: small fixed monthly baseline; scales with concurrent sessions (a mock-provider load test at M3 measures sessions per realtime instance).
  • GPU (dominant cost): cost_per_active_hour = gpu_$/h ÷ sessions_per_gpu. sessions_per_gpu for MiniCPM-o-class streaming is unmeasured (the authors report edge-device deployment under 12 GB RAM; server concurrency depends on quantisation, context length, and whether audio output is generated continuously). Illustrative sensitivity only (not a quote): at $1/h GPU, 2 sessions → $0.50/h, 6 sessions → $0.17/h per active session-hour. Plans and limits (voice seconds) must be set from the measured number in M8, with the cascade provider as the cost-controlled fallback.
  • Levers: quantised weights (GPTQ W4A16/GGUF builds exist), session max length, idle timeouts (socket per turn), per-plan concurrency caps, scale-to-zero outside demand, regional GPU price shopping, cascade for free tier.
  • Storage/egress: minimal by design (no audio/frames retained).

B5. Backup, DR, retention

PITR ≥ 7 days (RPO ≤ 5 min), daily logical dump to separate storage (30 days), quarterly restore drill (RTO ≤ 2 h), object storage versioning for non-ephemeral buckets, infra as config (render.yaml, Dockerfiles; Terraform when multi-cloud/enterprise requires), runbooks in docs/runbooks/ (deploy, rollback, key rotation, incident, restore, GPU outage → fallback).

B6. Monitoring, SLOs, alerting

SLOs: API availability 99.5% (monthly); realtime session start p95 ≤ 600 ms; turn first-audio p90 ≤ 2.0 s (with the real model; mock validates plumbing); tool verified-rate ≥ 95% for SAFE device tools; claim-guard trigger rate < 1% of tool turns; crash-free sessions ≥ 99.5%. Alerts: error budget burn, DB saturation, WS connection drops, provider failure/fallback activation, usage-limit anomalies (cost spikes per org), webhook failures, queue depth. Dashboards per milestone gate.

B7. Acceptance (deployment)
